# 上云方案对比：云服务器 vs 微信云开发 / 云托管

> 这是一份**决策备忘**，给项目负责人看。
> 结论先说：**「云开发更便宜」是个错觉**（对我们这个项目而言），
> 但它确实能**省掉 ICP 备案**这条关键路径。
> 「运维责任」能不能转移，取决于**买谁的托管服务**和**合同怎么写**，而不是取决于用不用云开发。

---

### 把我们的整套栈放到云托管上（账）

| 组件 | 云托管月费 | 说明 |
|---|---|---|
| API 容器（1核2G） | ≈ ¥96 | 我们的 NestJS，Dockerfile 可直接用 |
| Worker 容器（BullMQ 常驻，1核1G） | ≈ ¥72 | **云托管没有托管 Redis**，队列要么自建要么另购 |
| 云托管 MySQL（1 实例） | ≈ ¥307 | |
| Redis | 另购腾讯云 Redis | ¥100+ /月（BullMQ 依赖它） |
| COS + 流量 | ≈ ¥15 | |
| **合计** | **≈ ¥500~600 /月** | **≈ ¥6000~7200 /年** |

### 结论：钱的量级差 8~10 倍

| 方案 | 稳态年费 | 倍数 |
|---|---|---|
| 轻量服务器 2核4G（刊例价，自建 MySQL/Redis） | **¥663 ~ ¥734** | 1× |
| 微信云托管（容器 + 托管 MySQL + Redis + COS） | **≈ ¥6000 ~ ¥7200** | **≈ 9×** |

> **「客户不想为云服务器付费 → 换云开发」在钱上是反的。**
> 云开发/云托管是**按小时常驻计费**的，不管你有没有流量；
> 而轻量服务器是**包年包月**，流量小就是很便宜。
> 云开发的成本优势只出现在「流量巨大、按量付费」的场景。

## 二、那云开发到底强在哪？只有一个点，但它正好卡着我们

**✅ 免 ICP 备案。**
微信云开发/云托管给小程序分配的域名**已经备案**，
小程序通过 `wx.cloud.callContainer` / `callFunction` 调用**不需要配 request 合法域名**。

我们当前的硬卡点正是这里：
- 后端入口是 `http://8.160.116.34:18080`（**IP + HTTP**）；
- 微信要求合法域名必须 **HTTPS + 已备案域名 + 不能是 IP**；
- 自己买域名备案要 **7~20 个工作日**。

→ **如果客户希望「下周就能在手机上正常打开（不开调试模式）」，
云托管是目前唯一能立刻达成的技术路径。**

### 但迁移代价要算清楚

我们的后端不是「一个能跑的容器」这么简单：

| 组件 | 现状 | 迁到云托管的改动 |
|---|---|---|
| API（NestJS + TypeORM） | Dockerfile | **几乎不用改**（云托管跑容器） |
| MySQL | 自建容器 | 换成云托管 MySQL：改连接串 + 确认时区/字符集 |
| Redis | 自建容器 | ⚠️ **云托管没有托管 Redis** → 要么另购腾讯云 Redis，要么改造掉 Redis 依赖 |
| Worker（BullMQ 队列 + Outbox 派发） | 常驻容器 | ⚠️ 要变成**常驻云托管容器**（有最小实例费用），不是云函数 |
| MinIO（对象存储） | 自建容器 | 换成 COS：只改 `MINIO_*` 环境变量（已预留开关 ✅） |
| **云函数路线** | — | ❌ **要重写 Worker 与调度**，冷启动几百毫秒到数秒，首屏体验差 —— **不推荐** |

工作量估计：**云托管路线 1~2 周**（含联调与真机验证），
**云函数路线 3~4 周 + 架构降级**。

## 三、运维责任：能不能转移，取决于「买谁的托管服务」

把「运维责任」拆开看，一共四层：

| 层次 | 内容 | 自有服务器 | 云托管/云开发 | 托管数据库（COS/RDS/Redis） |
|---|---|---|---|---|
| ① 基础设施 | OS 打补丁、磁盘、机房、网络 | **我们**（最重） | **云厂商 SLA** | **云厂商 SLA** |
| ② 中间件 | MySQL/Redis 的备份、主从、慢查询 | **我们** | 云托管 MySQL = **云厂商**；Redis 另购 = **云厂商** | **云厂商** |
| ③ 应用 | 代码、配置、发布、监控告警 | **我们** | **我们** | **我们** |
| ④ 业务数据 | 校友个人信息的内容与授权 | **我们 + 客户** | **我们 + 客户** | **我们 + 客户** |

**结论**：
- 换成「云开发」，①② 层交给云厂商，**③④ 层仍然是我们** ——
  代码总得有人维护、出了业务问题总得有人查。
  所以「换成云开发就不用我们负责了」是**不成立的**。
- 真正能把①②层彻底转移的是**买云厂商的托管服务**：
  轻量/CVM（OS 层托管）+ TencentDB MySQL + Redis + COS。
  这套下来最便宜，而且**基础设施 SLA 由云厂商兜底**。
- ③④ 层（应用与数据）的责任，**只能靠合同划分**，靠技术手段划分不了。
  建议在服务合同里写清：
  - 云资源账号与费用归属（谁付钱、谁的主体）；
  - 可用性承诺与故障响应时限；
  - 数据导出与迁移协助；
  - 变更窗口与回滚责任。

## 四、数据合规（这一条容易被忽略，但对我们最要命）

系统里存的是**校友的姓名、地区、行业、毕业年份，以及加密后的联系方式**（手机/微信/邮箱，AES-256-GCM）。

| 方案 | 数据存放 | 顾虑 |
|---|---|---|
| 校园机内网 | 校园机房 | ❌ **不适合承载真实个人信息**（无等保、运维不规范、内网可达性依赖 VPN） |
| 自购云服务器 | 阿里云/腾讯云（乌兰察布） | 需客户主体备案；数据在云上，但**由我们自己掌控** |
| 微信云托管 MySQL | 腾讯云 | 数据在腾讯云；需客户与腾讯云签数据处理协议（小程序主体一般已有） |

> 无论选哪条，**数据库都必须在云上**（不能继续用校园机），
> 校园机最多保留一份**只读副本/备份**。
> 这一点跟「客户付不付服务器钱」无关，是合规底线。

## 五、我的建议（分三步，不要一次性做完）

### 第 1 步：现在（临时预览期，零额外成本）
- 后端仍在校园机 + 阿里云边缘（服务器都已经在跑，边际成本≈0）；
- 备案没下来之前，客户用**调试模式**或**离线演示版**体验；
- **不要**在备案下来之前往真实校友数据上迁。

### 第 2 步：正式上线（默认路线，省钱 + 数据自持）
**客户主体注册腾讯云/阿里云账号 → 买 2核4G 轻量服务器（¥663~734/年）→ 域名在客户主体下备案 → COS 换掉 MinIO。**
- 服务器与域名费用**走客户账号**（客户本来就要为小程序主体、认证、备案准备执照）；
- 我们负责部署、发布、监控、备份、故障处理，**这部分计进我们的服务费**；
- 责任边界：云厂商保基础设施 SLA，我们保应用，**明确写进合同**；
- 成本最低（比云托管省 9 倍），数据在客户自己的云账号里。

### 第 3 步：如果客户坚持「零运维、零服务器、且要立刻能用」
**微信云托管（CloudBase Run）+ 云托管 MySQL + TencentDB Redis + COS。**
- 免备案 → **下周就能正常打开**；
- 成本 ≈ ¥500~600/月（≈ ¥6000+/年），需要客户接受这个量级；
- 我们仍然负责应用层（③），工作量 1~2 周。

### 不推荐
**纯云函数**：Worker/BullMQ/Outbox 要重写，冷启动伤首屏，架构降级，收益不比云托管。

---

## 六、要问客户的三个问题（决定走哪条路）

1. **「服务器费用谁承担？」** —— 是客户自己买（走客户账号），还是我们包进服务费？
   → 这决定第 2 步还是第 3 步，也决定合同怎么写。
2. **「多久之后要在客户手机上正常打开（不开调试模式）？」**
   → 立刻要 → 云托管；等得起 1~3 周 → 备案 + 轻量服务器（更便宜）。
3. **「校友个人数据能否放在腾讯云？」**
   → 能 → 两条路都可行；不能 → 只剩第 2 步（自购云服务器）。
