# 内蒙古北京大学校友会数字化平台

# V1 全栈 MVP 项目建设计划

**项目代号：** NMG-PKU-Alumni
**版本：** V1.0
**项目性质：** 完整软件系统建设
**实施方式：** 本地 Agent 主导，私网服务器承担重型计算与构建
**目标：** 一次性建立完整、可运行、可测试、可持续迭代的校友会数字化平台。

# 0. 本轮项目目标与执行原则

本轮不是单纯的 HTML 原型优化，也不是技术方案调研。

本轮要求直接完成一套完整的 V1 MVP，包括：

1. 微信小程序前端。
2. NestJS 后端 API。
3. MySQL 数据库。
4. 校友会运营管理后台。
5. 文件上传与对象存储。
6. 用户身份认证与权限管理。
7. 校友通讯录。
8. 双向校友联系系统。
9. 资源与需求发布审核系统。
10. 活动发布与报名系统。
11. 通知系统。
12. Docker 容器化开发与测试环境。
13. 私网服务器远程构建体系。
14. 自动化测试、并发测试及数据备份体系。
15. 完整项目文档与部署说明。

**本轮完成标准：完整业务闭环，而不是页面数量或代码数量。**

项目完成后，应该可以：

- 启动整个 Docker 环境。
- 登录小程序测试账号。
- 提交校友认证。
- 在管理后台审核校友。
- 使用认证账号查询校友。
- 向其他校友提交联系申请。
- 由接收方接受或拒绝申请。
- 建立真实的数据库连接关系。
- 发布资源和合作需求。
- 由管理员审核并公开。
- 创建活动、报名活动。
- 在管理后台管理所有业务。
- 使用自动化测试验证核心流程。
- 通过 k6 测试并发和业务一致性。

当前暂不注册微信小程序账号，因此微信真实登录、正式微信消息推送及正式上线配置采用适配器和配置占位方式。其余业务不应因此停滞。

## 1. 产品基线与范围

### 1.1 保留现有 HTML V1

用户提供的 HTML 原型是当前产品的视觉和交互基准。

要求：

- 保留现有红白视觉体系。
- 保留燕园建筑与北疆文化元素。
- 保留四个一级栏目。
- 保留现有主要功能和业务构想。
- 不推翻已经获得客户认可的视觉方向。

将原始 HTML 保存为独立参考版本，不允许 Agent 直接破坏原始成果。

HTML V1 作为产品原型，不再承担正式业务系统的角色。

正式小程序应重新使用原生微信小程序技术实现。必要的二级页面在正式客户端中一次性规划并实现，不要求先把 HTML 原型改造成完整的多页面产品。

### 1.2 四个一级栏目

| ------ | ------------------------------------------------ |
| 首页   | 校友会动态、活动、公告、资讯                     |
| 通讯录 | 校友搜索、地区筛选、行业筛选、个人资料           |
| 连接   | 资源、需求、合作意向、双向联系                   |
| 我的   | 个人资料、身份认证、活动记录、连接记录、隐私设置 |

### 1.3 已确定的业务规则

以下决策必须贯彻到前端、后端、数据库和管理后台。

**校友身份认证**

- 用户填写个人及北大经历资料。
- 提交证明材料。
- 校友会管理员人工审核。
- 审核通过后才获得正式校友权限。
- 支持要求补充材料、拒绝及重新提交。
- 保留完整审核历史。

**校友之间建立联系**

- 双方通过申请和接受建立联系。
- 申请必须由接收方明确接受。
- 拒绝申请不产生正式连接关系。
- 不允许通过前端绕过授权直接获取联系方式。
- 双方联系方式独立授权，可撤回。

**资源与需求发布**

- 所有资源和需求必须人工审核。
- 未审核通过的信息不能出现在公开列表。
- 修改已发布内容后重新审核。
- 审核历史不可覆盖。
- 管理员拥有下架权限。

# 2. 总体技术架构

采用模块化单体后端 + 独立前端应用 + Docker 容器化部署。

## 2.1 技术栈

| 层次           | 技术选型                                  |
| -------------- | ----------------------------------------- |
| 小程序         | 原生微信小程序 + TypeScript               |
| 小程序组件     | TDesign Miniprogram + 自定义组件          |
| 管理后台       | Vue 3 + TypeScript + Vite                 |
| 管理后台组件   | TDesign Vue Next                          |
| 状态管理       | Pinia（管理后台）；小程序采用轻量 Store   |
| 服务端         | NestJS                                    |
| 数据库         | MySQL 8.4 LTS                             |
| ORM            | TypeORM                                   |
| 缓存与任务队列 | Redis + BullMQ                            |
| 文件存储       | MinIO（开发测试）/ OSS 或 COS（正式环境） |
| 反向代理       | Nginx                                     |
| API            | REST API + OpenAPI                        |
| 容器           | Docker + Docker Compose                   |
| 包管理         | pnpm                                      |
| 自动化测试     | Jest/Vitest + Playwright + k6             |
| 代码规范       | ESLint + Prettier + TypeScript Strict     |

依赖版本必须使用当前稳定且相互兼容的版本，并在项目初始化后锁定，不允许 Agent 在不同模块中随意升级依赖。

# 6. 并发、事务与一致性

并发是正式系统的基础能力，不是上线前简单加一个压力测试就能解决的。

## 6.1 总体原则

- API 无状态，支持多实例。
- MySQL 是业务数据唯一事实来源。
- Redis 不承担关键业务数据的最终一致性责任。
- 关键操作使用事务。
- 通过唯一索引防止重复数据。
- 通过原子状态更新避免重复审核。
- 通过幂等键防止重复提交。
- 通过乐观锁避免更新覆盖。
- 异步任务与用户请求解耦。

## 6.2 三类重点并发问题

### 双向连接

必须处理：

- A 与 B 同时互相申请。
- 同一申请重复点击接受。
- 两名用户重复建立连接。
- 拒绝后重复申请。
- 关系解除与联系方式授权冲突。

采用规范化连接对、唯一索引、事务及条件更新解决。

### 资源审核

必须处理：

- 两个管理员同时审核。
- 审核期间用户修改内容。
- 同一内容重复审核。
- 审核通过后重复发布。
- 已发布内容修改时被其他管理员同时处理。

采用状态版本号、审核快照和原子状态更新。

### 活动报名

必须处理：

- 同一用户重复报名。
- 多人同时争抢最后一个名额。
- 取消报名与其他报名请求竞争。
- 活动容量更新。
- 活动关闭时仍有请求进入。

采用唯一索引和事务内的容量条件更新。

## 6.3 异步任务

使用 Redis + BullMQ：

- 通知发送。
- 站内消息生成。
- 文件清理。
- 过期申请处理。
- 审核提醒。
- 定期数据维护。

重要通知采用数据库 Outbox 模式，先在业务事务中写入待发送事件，再由 Worker 投递，支持失败重试和幂等消费。

## 6.4 压力测试

使用 k6。

测试档位：

| 级别     | 虚拟用户                        |
| -------- | ------------------------------- |
| 基础     | 20                              |
| 常规     | 50                              |
| 压力     | 100                             |
| 扩展     | 200                             |
| 极限探索 | 500，视服务器资源和其他任务情况 |

测试接口：

- 登录。
- 通讯录查询。
- 资源列表。
- 个人资料。
- 联系申请。
- 联系接受。
- 资源提交。
- 活动报名。

必须进行并发业务正确性测试。

不能出现重复连接、重复报名、审核状态回退、资源未审核公开、联系方式越权访问。

初步性能观察指标：

- p50、p95、p99。
- 错误率。
- 数据库连接池等待。
- 慢 SQL。
- CPU、内存。
- Redis 队列积压。
- API 吞吐量。

性能目标应通过实际测试确定，不允许虚构已经达到的并发能力。
