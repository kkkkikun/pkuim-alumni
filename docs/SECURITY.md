## 1. 认证

- 密码：bcrypt（cost 10）单向哈希；管理员密码不落明文，不出现在任何接口响应。
- 令牌：JWT access token 2 小时；refresh token 30 天且**只存哈希**，登出与刷新轮换立即吊销。
- 微信凭据：`code` → `code2session` 全程在服务端；`session_key` 不下发、不落库、不进日志。
- Mock 登录仅在 `AUTH_MODE=mock|both` 时可用；正式上线置 `AUTH_MODE=wechat` 即关闭。
- **取值非法时按最严口径处理（fail-closed）**：`AUTH_MODE` 写错（如 `wechats`）不再退回 `both`
  （那等于把 Mock 后门重新打开），而是关闭 Mock 登录并打错误日志。
- **启动期校验**：生产环境缺 `JWT_SECRET` / 数据库口令 / MinIO 密钥，或 `CORS_ORIGINS=*`，
  或 `AUTH_MODE` 未显式设置 / 取值非法 / 为 `mock` —— **拒绝启动**（`src/config/config-validation.ts`）。
- **占位值识别不分隔符**：`change-me-xxx` 与 `CHANGE_ME_xxx` **同样**被判定为占位值 ——
  仓库自己的模板（`docker-compose.prod.yml`、`infra/env/env.prod.example`）用的就是下划线写法，
  上一轮的防线对自家模板完全无效（见 KNOWN-ISSUES #173）。
- **管理员口令没有默认值**：仓库里公开的 `Admin@2026` **不再是任何路径的兜底值** ——
  管理端建号必须提供初始口令（DTO 必填），Seed 在生产环境要求显式提供强口令、
  且不再重置已存在账号的口令（见 KNOWN-ISSUES #175）。

## 2. 授权

- 用户身份阶段（游客 / 已登录 / 待审核 / 已认证）由后端 `AlumniStageGuard` 强制，
  前端隐藏按钮不构成安全边界。
- 管理端权限点由 `PermissionsGuard` 校验；用户令牌不能调用管理接口，管理员令牌具备独立权限集合。
- 越权访问统一返回 403，不泄露资源是否存在（目录中未公开资料返回 404）。

### 2.1 进程内缓存与撤权延迟（第三轮引入；第五轮补上跨实例失效总线）

> ⚠️ 本节是**先定口径、再写代码**的：口径写在前面，实现才允许落地。
> 下面每条都是**可核对的行为承诺**，不是「以后再说」。

#### 2.1.1 缓存了什么、没缓存什么

| 数据 | 是否缓存 | 原因 |
|---|---|---|
| 管理员的**角色 / 权限点**（RBAC 解析结果） | ✅ 进程内 TTL 缓存 | 每个管理端请求都要重算 4 条 SQL（`admin_users` + `admin_user_roles` + `role_permissions`），是管理端最大的单点开销 |
| 管理员账号的**启用状态** | ✅ 与 RBAC 同一条缓存 | 见下方「撤权延迟」 |
| 地区 / 行业**字典**（含校友计数聚合） | ✅ 进程内 TTL 缓存 | 每次请求都做一次 `alumni_profiles JOIN users` 的全表 GROUP BY，小程序冷启动必打 |
| 资讯分类、系统设置 | ✅ 进程内 TTL 缓存 | 同上：写多读少、变更低频 |
| **未读通知数**、任何需要实时性的数据 | ❌ **绝不缓存** | 缓存未读数会让「红点」长期不消，用户会以为消息丢了 |

> 共享失效总线（2.1.5）**只传「谁的缓存该作废」**，不改变上表：
> 需要实时性的数据**既不进缓存，也不进总线** —— 未读通知数每次实时 `COUNT`。

#### 2.1.2 TTL 与撤权延迟（**最长 TTL 的撤权延迟**）

| 缓存项 | TTL | 最长撤权/陈旧延迟 |
|---|---|---|
| RBAC（角色 / 权限点 / 账号状态） | **30 秒**（`RBAC_CACHE_TTL_SECONDS`，上限 60 秒） | **≤ 30 秒**（默认配置；配到硬上限时 ≤ 60 秒） |
| 字典 / 分类 / 系统设置 | **60 秒**（`DICT_CACHE_TTL_SECONDS`，上限 300 秒） | ≤ 60 秒（默认配置；配到硬上限时 ≤ 300 秒） |

- RBAC 缓存 TTL **硬上限 60 秒**（配置值超过 60 秒会被夹到 60），
  理由是「降权后最长 60 秒内仍可操作」是安全语义，必须有明确上界。
- TTL 配置**允许设为 0** = 关闭缓存（完全回到每请求重算的行为），便于排障与压测对照。
- 两个 TTL 由 `RBAC_CACHE_TTL_SECONDS` / `DICT_CACHE_TTL_SECONDS` 控制，
  生产环境通过 `.env.prod`（模板 `infra/env/env.prod.example`）与 `docker-compose.prod.yml`
  的 `environment:` 暴露；缺省值与本文档一致（30 秒 / 60 秒）。

#### 2.1.3 主动失效（降权 / 停用即刻生效，不等 TTL）

TTL 只是**兜底**，不是唯一手段。以下写操作在**同一事务提交后**立刻清掉相关缓存条目，
因此在本进程内**撤权是即时的**（延迟 0）：

| 操作 | 失效范围 |
|---|---|
| 管理员**停用**（`PATCH /admin/users/:id`，`status='disabled'`） | 该管理员的 RBAC 缓存 |
| 管理员**改角色**（`PATCH /admin/users/:id`，`roles` 变化） | 该管理员的 RBAC 缓存 |
| 管理员**新增**（`POST /admin/users`） | 无需失效（此前无缓存条目） |
| 资讯**分类**增删改 | 分类缓存 |
| 系统设置**写入**（`PUT /admin/settings`） | 系统设置缓存 |

> 前两行（停用 / 降权）**跨实例**也即时生效：事务提交后向共享失效总线发布一条失效事件，
> 其它实例收到后清掉本地对应条目（口径见 2.1.4 与 2.1.5）。

#### 2.1.4 撤权延迟的三档上界（**多实例部署**）

「停用 / 降权之后，多久生效」是一个**安全语义**，必须有明确上界，而不是「不知道会缓存多久」。
本仓库的口径分三档：

| 部署形态 | 总线状态 | 撤权延迟上界 | 依据 |
|---|---|---:|---|
| **单实例** | 不适用 | **0** | 写操作与主动失效在**同一个进程**里，事务提交后立刻清掉本地条目 |
| **多实例** | **总线可用** | **0** | 写操作在事务提交后向共享失效总线发布一条**失效事件**，其它实例收到后立刻清掉本地对应条目 |
| **多实例** | **总线不可用**（Redis 挂了 / 订阅断开） | **≤ TTL**（默认 ≤30 秒，配到硬上限时 **≤60 秒**） | 失效事件送不到 → 只能等本地缓存自然过期；**这是兜底，不是永久放行** |

- 「总线不可用」时**管理端写操作照常成功**：不抛错、不回滚业务写（见 2.1.5 的降级路径）。
- 任何一档都**不得**退化成「降权后无限期可操作」：最坏情况就是 TTL 上界（≤60 秒），
  且 TTL 本身有**硬上限 60 秒**（配置写大也会被夹回 60）。
- **单实例不需要总线**：本地主动失效已经是 0 延迟；总线只是把「跨实例」这一档补齐，
  不引入任何新的基础设施（Redis 已在依赖里：限流 / 队列 / 浏览计数都在用）。

#### 2.1.5 共享失效总线（Redis pub/sub）

**目的**：让「停用 / 降权」在**别的实例**上也立刻生效（第 2.1.4 节的第二档）。

- **只传失效事件，不传权限内容**：
  总线上流动的消息形如 `{"kind":"admin","adminId":42}` —— 只有「**谁的缓存该作废**」，
  **不含任何权限点、角色名、联系方式或业务数据**。
  权限点仍然由**每个实例自己**从库里算（口径与单实例时完全一致），
  所以总线不是一条「跨实例共享敏感数据」的通道。
- **频道名走配置，不写死**：`RBAC_INVALIDATION_CHANNEL`，默认基准名 `nmg:rbac:invalidate`。
  **生效频道按环境隔离**（在命名空间后插入环境段）：
  `nmg:prod:rbac:invalidate` / `nmg:dev:rbac:invalidate` / `nmg:test:rbac:invalidate`
  —— 测试库的事件**不可能**打到生产实例的订阅端。
- **发布时机**：管理端写操作（停用 / 降权）**事务提交之后**才发布 ——
  事务回滚了却把失效事件发出去，会让其它实例白白丢掉缓存（只丢性能，不丢正确性），
  但没必要。
- **降级路径是硬要求**：
  - Redis 不可用 / 订阅断开时，**管理端写操作照常成功**（200）：
    **不抛错、不回滚业务写**、不把 Redis 的故障变成管理端的 5xx；
  - 此时撤权延迟回落到 **TTL 上界**（≤60 秒），**不是永久放行**；
  - 总线恢复后自动重新订阅（不重启进程）。
- **未读通知数依旧不缓存**：总线**不承载**任何「需要实时性」的数据 ——
  未读通知数仍然每次实时 `COUNT`（见 2.1.1 的表格与 `GET /me/summary`），
  红点不能因为「总线不可用」或「多实例」而长期不消。
- **总线只承载 RBAC 失效事件**：字典 / 分类 / 系统设置的跨实例失效**不在本总线上**
  （它们的跨实例陈旧上界仍是各自的 TTL，见 2.1.2）—— 记在 `docs/KNOWN-ISSUES.md`。

#### 2.1.6 缓存不得成为绕过鉴权的路径

- RBAC 缓存只缓存**「这个管理员有哪些权限点」**这一事实，
  **不缓存**「这个请求是否被允许」—— 每次请求仍然要走 `PermissionsGuard` 逐个权限点比对。
- 缓存**不跨用户共享**：键是管理员 id，不含通配。
- 缓存**不含任何业务数据**（不含联系方式、不含隐私字段），进程重启即清空。

### 2.2 浏览计数（`viewCount`）的最终一致口径

> 第三轮引入（**先定口径、再写代码**）。

- **为什么改**：此前每次浏览都直接 `UPDATE articles SET view_count = view_count + 1`，
  热门文章的所有浏览者会**串行争抢同一行锁** —— 这一行就是热点。
- **现在的做法**：浏览只在 **Redis** 里 `HINCRBY` 计数（无行锁）；
  累计到 **20 次**或到 **60 秒**周期时，才把增量**一次性**写回数据库
  （仍然只动 `view_count` 一列，`updated_at = updated_at`，浏览不产生任何副作用）。
- **一致性口径**：`viewCount` 由**即时一致**改为**最终一致**。
  - 详情接口返回的 `viewCount` = 「库里的基线值 + 尚未落库的增量」，
    所以**用户看到的数字当场就是对的**；
  - **数据库行里的 `view_count` 可能滞后**（最多一个刷回周期 = 60 秒）。
- **Redis 不可用时**：**降级为直接写库**（与改动前完全一致）——
  计数不会丢，只是又回到了「每次浏览写一行」的旧模式。
- **并发安全**：刷回用 Lua 脚本「原子取走」增量，
  两个实例同时刷回**不会重复计数**。

## 3. 隐私与联系方式（最高优先级）

1. 联系方式存 `private_contacts`，AES-256-GCM 加密，密钥由 `JWT_SECRET` 派生（不同环境自动隔离）。
2. **列表接口永不 SELECT 联系方式列**；通讯录、连接列表、资源列表均无该字段。
3. 对方联系方式可见需同时满足四个条件：
   - 存在 `connection_pairs.status='active'`；
   - 我方 `alumni_profiles.allow_contact_share = 1`；
   - 对方 `alumni_profiles.allow_contact_share = 1`；
   - 存在 `contact_share_grants.allow = 1`（我方与对方各一条）。
4. 撤回授权立即生效（授权记录置 0）；解除连接关系时在同一事务内撤销双方授权。
5. 通讯录只返回 `users.stage='verified'` 且 `show_in_directory=1` 的校友，并按
   `show_college / show_industry / show_region` 做字段级裁剪。
6. **学号由服务端脱敏后落库**（`student_id_masked` 保留首尾各 2 位，中间为 `*`）：
   客户端提交完整学号也只会存成脱敏值；后台用完整学号搜索仍能命中（按同一规则脱敏后匹配）。
7. **证明材料只接受私有桶资产**：`visibility='public'` 的文件被当作证明材料引用时返回 400，
   且不会写进证明材料关联表（public 桶里的对象拿到地址即可下载，不能承载私密材料）。
8. 证明材料存私有桶，仅审核权限可取短期签名 URL。
9. **解除连接之后，连接详情不再返回对方资料**：非 `active` 的关系一律 404
   （此前详情接口不校验关系状态，与列表口径不一致 —— 见 KNOWN-ISSUES #177）。

## 4. 输入与注入

- 所有入参经 `class-validator` 校验（长度、范围、枚举、正则），`ValidationPipe` 白名单模式拒绝多余字段。
- 数据访问统一走 TypeORM 参数化查询，无字符串拼接 SQL。
- 文件上传校验 MIME、扩展名与大小；对象 key 由服务端生成，不使用用户提供的路径。

## 5. 传输与暴露面

- 服务器只监听私网地址，对外暴露经 Nginx；不开放 Docker TCP 2375，不修改服务器 SSH 配置。
- 数据库 / Redis / MinIO 端口仅绑定 `127.0.0.1`。
- **CORS 白名单精确匹配**（`src/config/cors.ts`）：
  - 生产环境 `CORS_ORIGINS` 不得为 `*`（启动期校验直接拒绝启动），也不接受任意 Origin；
  - 白名单外的 Origin **拿不到任何 CORS 响应头**，预检请求返回 403；
  - `*` 仅在非生产态可用，且此时**不带凭据**（不再「反射任意 Origin + credentials」）。
  - **只接受配置里逐条列出的具体域名**：子域通配（`https://*.example.com`）**不认**，
    启动期校验也把带 `*` 的 origin 判为非法（见 KNOWN-ISSUES #176）。
- **安全响应头应用层与 Nginx 层都覆盖**（`src/common/middleware/security-headers.ts` +
  `infra/nginx/nginx.conf`）：`X-Content-Type-Options`、`X-Frame-Options: DENY`、
  `Referrer-Policy`、`Permissions-Policy`、`X-Permitted-Cross-Domain-Policies`、
  `Cross-Origin-Opener-Policy`、`Content-Security-Policy`、`Strict-Transport-Security`（HTTPS/生产态）。
  API 端口可绕过 Nginx 直连，这层由应用自己保证。
  - 管理后台的静态资源（`infra/nginx/admin-web.conf` 的 `location /assets/`）也覆盖同一组头 ——
    nginx 的 `add_header` **不跨层继承**，该块自己出现 `add_header` 就会丢掉父层的全部安全头
    （见 KNOWN-ISSUES #178）。
- **反向代理信任**：`TRUST_PROXY_HOPS`（默认 1）让限流按**真实客户端 IP** 计数 ——
  此前 `req.ip` 恒为 Nginx 容器地址，所有匿名请求共用一个计数桶。

## 6. 频率与滥用

- 登录 / 刷新：20 次/分钟；写接口 30 次/分钟；读接口 240 次/分钟（按用户或 IP，固定窗口计数于 Redis）。
- **计数桶按「身份 + 接口类别」（auth / write / read）**，不是按路由处理器 ——
  逐路由分桶会让实际阈值放大到文档承诺的数倍。
- **认证失败的请求同样计额**：限流守卫排在 JWT 守卫之后，伪造 / 过期令牌的请求此前在到达限流前
  就被 401 拒掉，等于完全不受保护。现在认证失败先按 IP 计一次额度，超阈值直接 429
  （见 KNOWN-ISSUES #179）。
- **类别判定先看 handler 名再看 HTTP 方法**：登录 / 刷新端点全是 POST，
  若先按方法判成 write 档，「登录 20 次/分钟」这一档就形同虚设。
- 限流中间件在 Redis 不可用时**降级放行**（可用性优先），不阻断业务。

## 7. 审计

- 管理端关键操作（审核、发布、下架、账号状态）写入 `admin_action_logs`（只追加）。
- 审计日志记录**来源 IP**（`admin_action_logs.ip`；此前该列从未被写过，管理端该列恒为空）。
- **审计记录受数据库保护**：`admin_action_logs.admin_id` 的外键是 `ON DELETE RESTRICT`，
  删除管理员账号**不会**连带删掉他的审计痕迹（此前是 `CASCADE`，等于「删账号即删证据」）。
- 资源审核历史 `resource_post_reviews` 与认证审核历史 `verification_reviews` 只追加，不覆盖。
- 连接申请历史只追加，接受/拒绝/撤回都留痕。
- **第三轮补齐**：`POST/PATCH/DELETE /admin/articles/categories` 与 `PUT /admin/settings`
  这 4 个写端点此前**完全没有**审计记录（`docs/SECURITY.md` 第 7 节列举的关键操作都留痕，
  这几个是漏的）。现在：
  - 业务写与审计写进**同一事务**（审计写失败时业务写一起回滚 ——
    否则会出现「内容已改但没有审计痕迹」，事后无法追溯）；
  - 审计动作名：`category.create` / `category.update` / `category.delete` / `setting.update`；
  - `setting.update` 的审计**不记 `value`** —— 系统设置里可能放敏感配置，
    审计日志是要长期留痕的表，不该成为泄密面（只记 `key` 与 `description`）。

- [x] **Mock 登录收敛**：`AUTH_MODE` 在配置、启动校验与登录路径三处都收敛；
  非 `wechat` 之外的取值按 fail-closed 处理；`AUTH_MODE=mock` 在生产环境拒绝启动。
- [x] **CORS 收敛到白名单**：只接受配置里列出的具体域名，不接受通配符、不接受任意 Origin；
  正向与负向用例齐备（`test/integration/security-hardening.e2e-spec.ts`）。
- [x] **安全响应头**：应用层与 Nginx 层都覆盖（见第 5 节）。
- [x] **审计只追加的数据库保护**（见第 7 节）。
- [x] **占位值识别不分隔符**（第二轮）：`CHANGE_ME_xxx` 与 `change-me-xxx` 同样被拒，
  仓库自己的模板不再能绕过启动期校验；`.env.example` 与模板都写明了生成方式
  （`openssl rand -hex 32`）。
- [x] **部署模板与启动期校验对齐**（第二轮）：生产模板与 compose 的默认 `AUTH_MODE`
  不再是 `mock`（否则按仓库文档部署会起不来），但生产用 `mock` 依然被拒绝启动。
- [x] **管理员口令无默认值**（第二轮）：`Admin@2026` 不再是任何路径的兜底值；
  Seed 在生产环境要求显式提供强口令，且不再重置已存在账号的口令。
- [x] **CORS 只认具体域名**（第二轮）：子域通配一律不认（启动期也判为非法）。
- [x] **认证失败的请求也计额**（第二轮）：伪造 / 过期令牌不再绕过限流。
- [x] **共享失效总线：跨实例撤权立刻生效**（第五轮）：
  多实例部署时「停用 / 降权」不再要等 TTL（≤60 秒）——
  管理端写操作在**事务提交后**向共享失效总线发布一条**失效事件**（只含「谁的缓存该作废」），
  其它实例订阅后立刻清掉本地条目（口径见第 2.1.4 / 2.1.5 节）；
  总线不可用时**写操作照常成功**，撤权延迟回落到 TTL 上界。
