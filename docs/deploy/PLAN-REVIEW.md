## 二、开发进度盘点（回答「我们现在到哪了」）

你说「没把握清楚进度」——这个感觉的来源是**把「开发」和「流程」混在同一条进度条上看**。
拆开看，进度是清楚的。

**一句话：工程实现层面已经接近收尾。**

### 2.2 剩余工作的性质拆分 —— 这才是「感觉没底」的真正原因

| 类别 | 内容 | 归谁 | 能否压缩 |
|---|---|---|---|
| **A 写代码** | 生产域名配置拆分、AppID/Secret 换绑、OSS 适配、nginx 虚拟主机、`AUTH_MODE` 收口 | **我们** | 可控，约 2~3 周 |
| **B 跑验证** | 回归测试（**已自动化，15 分钟跑完 24 步**）、真机测试、弱网测试、UAT | 我们 + 客户 | 真机/UAT 必须占人天 |
| **C 外部流程** | 采购、ICP 备案、**小程序备案**、微信正式版审核 | 客户 / 管局 / 微信 | **完全不可压缩** |
| **D 等客户** | 正式内容（业务库现存 41 处「【虚构】」标记）、验收签字、反馈轮次 | **客户** | 取决于客户响应速度 |

> **结论：我们的时间不是瓶颈。** 关键路径是 **C（外部流程）**，
> 而 C 的启动开关在客户手上（拍板采购 + 交主体材料）。
> A 和 B 完全可以和 C **并行**推进，不需要等备案。

### 2.3 一个需要老板知道的好消息

**客户现在就能看，不需要等到 2027-01。**
把已上传的 0.7.0 在公众平台「设为体验版」+ 把客户加进体验成员，**5 分钟**，
客户即可从微信「小程序助手 → 体验版」进入，且**体验版本身没有过期时间**
（7 天是二维码的寿命，不是体验版的寿命）。
当前 0.7.0 是离线演示模式，**不请求后端**，所以不需要开调试、不需要备案域名。

## 三、逐条评审：6 处建议修正

### 3.1 ✅ 采纳并更正我方文档：「购买时长 ≥ 3 个月」≠「运行满 3 个月」

排表写「购买时长须达到 3 个月及以上（含续费累计）；购买 1 年满足该时长要求，
**不需要先运行满 3 个月**」——这条**纠正了我们此前的错误前提**。

我方 `docs/SELF-CHECK-AND-SCHEDULE.md` 原先写「部分省份要求服务器**运行满 3 个月**」，
并据此给出「2027-03~04」的保守档。该前提不准确，**已更正**（保守档改为 2027-02~03）。

**影响**：不必为了凑时长延后下单，采购越早越好这条结论**反而更成立**。

### 3.2 ⚠️ 「真实微信登录 2~3 个工作日」高估了

微信登录**全链路早已实现**：`apps/api/src/auth/providers/wechat-auth.provider.ts`
直接调 `sns/jscode2session` 换 openid；从 0.5.0 起上传的版本就是
`--mock-login false` 真实登录模式。

实际工作只是「换客户自己的 AppID / AppSecret + 重新配置 + 联调」，
**约 1 个工作日**。这不影响整体工期，但排期表里的分项估算应更准，否则老板会以为
这块是大头。

### 3.3 ⚠️ 「隐私及运营内容 2~4 个工作日」不是我们的工作量，是**客户的交付期**

排表把它放在「应用调整工作」里，容易被读成我们的活儿。实际是：
业务库 `seeds` 里有 **41 处「【虚构】」标记**，articles / events / notices 共 **22 条**
全是虚构内容，正式版必须全部替换为校友会确认的真实内容。

**这条应单列为「客户提供正式内容」的交付期风险**，并挂到排表第六节
「需老板/校友会尽快确认的事项」下面 —— 它和备案材料一样是客户侧阻塞项。

### 3.4 ⚠️ 「全面测试与验收 4~6 个工作日」应拆开

其中**回归测试已经自动化**：24 步回归链（42 集成套件 / 42 小程序单测 / 22 层校验
及其反向验证）**跑完约 15 分钟**，且已接入 CI 闸门。

真正需要人天的是：真机测试、弱网/异常场景、备份恢复演练、客户 UAT —— 约 **3~4 天**。
把自动化已完成的部分算作人工工作量，会让老板低估我们的执行效率、高估工期。

### 3.5 ⚠️ 补一条：**小程序备案**要进我们的技术清单

排表第三节第 3 步已正确列出「微信小程序备案（工信部信管〔2023〕105 号，最长 20 个工作日）」，
**但我们自己的 `docs/` 里完全没有覆盖这件事** —— 之前的部署文档只写了 ICP 备案。

这是两份手续、两条时间线、两个受理主体，**必须并行办理**。已记入我方文档待办。

### 3.6 ⚠️ 补一条：**客户现在就能看**

排表从头到尾没有体现「演示不受备案阻塞」。向老板汇报时应明确：
**演示是今天就能给的**（设体验版 5 分钟），备案卡住的只是「正式发布」。
这一条对项目预期管理很重要 —— 否则老板会误以为要到 2027-01 才能给客户看东西。

### 3.7 ⚠️ 补一条安全项：管理后台的访问控制

排表提到「admin.域名 作为管理后台域名」，但没提**管理后台的访问控制**。
管理后台是对公网暴露的后台，建议在生产配置里加上：
IP 白名单，或强制二次认证 / 强密码策略，或改为仅内网 + VPN 访问。
这属于 `AUTH_MODE` 收口那一组生产安全配置的一部分（我们已有 `ADMIN_*` 角色与权限体系，
不额外开发，但配置项要写进上线检查单）。

## 四、被漏掉的「第 0 号风险」：微信小程序 AppID 的注册主体

排表第六节第 5 条提到了「现有微信小程序 AppID 的注册主体、管理员及备案状态」，
**但没有把它标成第 0 号阻塞项**。

**为什么它排第一**：小程序备案要求**注册主体与备案主体一致**。
我们现在用的 AppID 是 `wx6761deb1125d858f`（测试期间注册）。

- 若它注册在**个人**名下 → 小程序备案**做不了**，也无法用校友会主体配置服务器域名
  → 正式版这条路直接不通，**必须先注册或转让**；
- 若它注册在**校友会主体**名下 → 这条风险直接消失。

**这件事的排查成本几乎为零（去公众平台看一眼），但它的后果最大**，
而且它比服务器采购更早成为阻塞项。建议老板今天就确认。

> 补充一个自查发现：今天已经把小程序端的**离线演示模式**做完整了
> （不请求后端、带「演示数据模式」提示条、演示内容全部带「【虚构】」标记），
> 这意味着**即使换 AppID 这件事卡住，客户体验演示也不会被阻塞**。

## 五、我们对这份排表的整体判断

| 维度 | 判断 |
|---|---|
| 采购建议（4核8G / 阿里云 / 呼和浩特 / ¥1159） | ✅ 与我们的独立测算一致（实测基线：7 容器工作集约 1.5 GB，业务库仅 12 MB） |
| 域名与账号归属建议 | ✅ 正确且重要（放校友会实名账号，不放开发人员个人账号） |
| 「只买一个域名，用 api./admin. 子域名」 | ✅ 正确 |
| ICP 备案时长口径（1~22 工作日） | ✅ 保守可信 |
| 「备案等待期并行推进应用调整」 | ✅ 正确，这是排期成败的关键 |
| 风险三档（顺利/基准/保守） | ✅ 分档合理，建议保守档再留一轮「客户反馈多轮」的缓冲 |
| 分项工作量估算 | ⚠️ 3 处高估（见 3.2 / 3.3 / 3.4），整体工期不受影响 |

**结论：可以用。** 建议在第 3.6 条补上「客户现在就能看」、
第 4 节补上「AppID 主体核查」作为第 0 号事项。
