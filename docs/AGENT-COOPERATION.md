# 人机协作约定：本地会话 × 云端 Agent

> 记录 2026-11-22 起，「本地人工会话」与「云端 dsh-superagent」在同一仓库
> （`kkkkikun/pkuim-alumni`）并行作业时的分工、仲裁流程与已知风险。
>
> **为什么需要这份文档**：两边都会改同一批文件（`infra/scripts/`、`docs/KNOWN-ISSUES.md`、
> `docs/TEST-REPORT.md`、`.agent/dispatch-queue.json`），
> 而**两边都不知道对方正在改什么** —— 于是撞编号、撞内容、互相覆盖。
> 这份文档就是那份「互相知道」的凭据。

## 一、两边是什么关系

| | 本地人工会话 | 云端 Agent |
|---|---|---|
| 形态 | 常驻在开发者终端的 MiniMax Code 会话 | 服务器上的 `dsh --profile pkuim`（Router/Worker 分层） |
| 仓库副本 | `~/MyProject/pkuim-alumni`（本机） | `~/src/pkuim-alumni`（服务器） |
| 身份 | kikun（仓库所有者） | `LL-ki`（agent 账号） |
| 提交方式 | 直接提交到 `master` | 开 `agent/<任务>-<hash>` 分支 → PR → CI 绿 → 自动合并 |
| 选题 | 客户反馈 / 交付节点驱动 | **自主**：按仓库自己记录的缺口（`docs/KNOWN-ISSUES.md` 等）挑 |
| 擅长 | 需求解读、真机验证、跨系统协调 | 穷举式对账、反向验证、跨轮次持续推进 |

**分工原则（2026-11-22 确认）**：

- **选题仍归 Agent** —— 它已经自主跑了 17 轮，穷举对账这类活它比人做得全。
- **监控与仲裁归人工会话** —— 只接两类必然发生的事：
  1. **链路断点**：隧道 / 节拍器 / watchdog / profile 卡死 → 救火；
  2. **两边撞车**：编号冲突、同一文件并行改动 → 裁决并落成。

## 二、编号仲裁：为什么会撞车，怎么解

### 现象

`docs/KNOWN-ISSUES.md` 的条目编号是**全局唯一且连续**的（`### 204.`、`### 205.` …）。
两边在**同一轮次**（「第十七轮」）各自开了新号：

- 人工会话：#204「校园机 API 代码旧一轮」、#205「api 镜像缺部署产物」
- Agent：#204「两层结论从未比对」、#205「read-visibility 反向验证补齐」、#206「--json 报告被截断」

结果是 `git merge` 在 `docs/KNOWN-ISSUES.md` 上冲突，且**两边各自看自己的编号都没错**。

### 处置规则（已验证可行）

1. **双方条目全部保留**，一个都不删。
2. **人工会话这一侧（较早合入 master）的编号不动** —— 它们已经在 master 上、已被
   `docs/UI-FEEDBACK-FIX-2026-11-22.md` 等文档引用，改号会连带改引用。
3. **Agent 那一侧顺延**到当前最大编号之后（本次 204/205/206 → 207/208/209）。
4. **同步修正交叉引用**：`docs/TEST-REPORT.md`、`.agent/dispatch-queue.json` 里
   提到这些编号的地方一并改（改完要 `json.load` 验一次仍合法）。
5. 改完核一次**编号唯一性**（无重复）再提交。

### 长期做法

- **Agent 新增条目时，继续沿用「当前最大编号 + 1」的习惯**（它 17 轮都这么干），
  不要求它改变写法 —— 冲突由人工会话在合并时裁决，代价可控。
- 巡检脚本会**自动检查编号唯一性**，一旦重复立刻报出来（见第四节）。

## 三、合并顺序：谁先谁后

当前实际状态（2026-11-22 17:20）：

- GitHub `master` = Agent 的 PR #46 已合并（`f7d161f`）+ 人工会话的 9 个提交（`bfaba89`）。
- Agent 的第十八轮（`opt-018`）正在跑，**基线是含真机整改的新 master**。

推荐的日常顺序：

1. Agent 的 PR 先合（它有 CI 门禁兜底）；
2. 人工会话再把本地 `master` 合到最新 `origin/master`（`git merge origin/master`），
   **一次只解一个冲突点**（当前就只 `docs/KNOWN-ISSUES.md` 一个）；
3. 本地跑全量校验 + 校园机跑 24 步回归链；
4. 推送。分支保护对管理员放行（`enforce_admins: false`），但**推送前必须自己跑绿** ——
   绕过了 GitHub 门禁，就更要自己补上。

⚠️ 不要在 Agent **还在往 PR 分支推**的时候把 master 合进它的分支（force push 会打断它的工作区）；
要解冲突就在自己这边合并。

## 四、巡检：一眼看清链路

```sh
bash ~/anyProject/dsh-superagent-setup/server-setup/agent-loop-status.sh
```

覆盖七段：本机隧道 → 服务器出网 → dsh profile 活体 → 节拍器/watchdog/进程 →
GitHub 派活链路 → CI 门禁 → 本地仓库同步状态与编号唯一性。
任一段异常即退出码非 0，并把异常项列在末尾。

### 巡检脚本自己也踩过的坑（值得记）

第一次写的时候用了 `pgrep -af 'watchdog'`，结果**永远匹配到系统自带的 `[watchdogd]`**
（内核看门狗，PID 很小、运行很久），于是「watchdog 在跑」这一项**恒绿** ——
真正的 `watchdog-loop.sh` 挂掉也不会报警。
同类地，`pgrep -af 'agent-dispatch-ticker'` 会**匹配到 pgrep 自己**。
现在两个判据都改成了精确匹配脚本名 + 排除 `pgrep` 自身。

> 这条坑与本仓库反复出现的那条教训是同一条：
> **绿灯不等于验的是你以为的那个东西。** 监控脚本本身也要有「假阳性」防线。

## 五、已知风险（按严重程度）

| 风险 | 现状 | 影响 |
|---|---|---|
| **模型侧配额**（coding plan 5 小时窗口） | 唯一硬上限，Agent 会在会话中途被掐断 | 那一轮的未提交产出丢失；节拍器能「续上」，但**不能保证不丢** |
| **服务器出网靠本机隧道** | 本机 WSL 的 Clash 隧道 → 服务器；WSL 随 Windows 重启**不会自动起** | 隧道断 → 服务器变瞎 → Agent 停摆（已发生过两次，各 12 小时） |
| **Windows 重启后 WSL 不自启** | 手册第 10.7 节记着，仍未解决 | 同上；`systemd --user` 只管 WSL 起来之后的事 |
| **仓库已转公开** | 为绕开 GitHub free 账号的私有库 Actions 限额 | 代码公开；此前泄露过的 DB / Redis / 管理台口令**建议轮换** |
| **两边并行改同一批文件** | 已发生一次编号冲突 | 由人工会话按第二节规则仲裁 |

## 六、人工会话的固定动作（接手后照做）

1. 每次开工先跑一次 `agent-loop-status.sh`，确认链路绿。
2. 收工前把本地 `master` 与 `origin/master` 对齐（合并 + 解冲突 + 验证 + 推送），
   **不要让两边长期分叉** —— Agent 看不到本地未推的改动，会重复劳动。
3. 合入 Agent 的 PR 后，核 `docs/KNOWN-ISSUES.md` 编号唯一性。
4. 客户反馈驱动的改动，**走真机验证 + 第 23 层校验**（见
   `docs/UI-FEEDBACK-FIX-2026-11-22.md`），不要只靠单测。
