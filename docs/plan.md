## 0. 硬性原则（贯穿所有 Phase）

1. **完整业务闭环优先**：不交付空接口、不交付假数据冒充后端、不停留在架构设计或静态页面。
2. **统一契约**：所有应用通过 `packages/contracts` 访问后端；数据模型以 `docs/DATABASE-DESIGN.md` 为唯一事实来源。
3. **重型任务在服务器执行**：依赖安装、Docker 构建、后端编译、集成测试、批量数据生成、并发压测
   全部在学校私网服务器（`sqserver`，128 核 / 295 GiB）执行。
4. **保护既有环境**：容器/数据卷前缀 `nmg-`、Compose 项目 `nmg-pku-alumni`、宿主端口 18xxx 段；
   禁止 `docker system prune`、禁止动 `swload-*`（SchoolWall 压测栈）等既有资源。
5. **不伪造结果**：测试、压测、部署结果必须真实执行并记录；未完成的能力明确标注「待配置」。
6. **阶段交付模板**：每个 Phase 结束时在本文档追加「交付记录」，含交付物、测试结果、问题记录、下一步计划。

## Phase 27 — Worker 投递链路：三处静默失败与「整层无覆盖」的流程缺口

**起因**：审计 Worker 的 Outbox → 队列 → 投递链路时发现，
这一层**完全没有被任何测试覆盖过** —— 前面 16 步全部走 HTTP 接口，
而投递是独立进程 + 独立中间件（BullMQ/Redis）。
于是三处「不抛异常、不影响响应码」的失败长期存在而完全不可见。

- [x] **#95** BullMQ 对**相同 jobId** 的 `add` 直接忽略
      → 失败后回退时 `attempts` 没有递增 → `jobId` 不变
      → dispatcher 重投被**静默吞掉** → 该通知**永远**投不出去，控制台零报错
      → `jobId` 改为携带 `attempts`（`buildJobId()`），回退路径必须 `attempts + 1`
- [x] **#96** 更新 `notification_deliveries` 不校验 `affectedRows`
      → 投递记录不存在时仍把事件标记 `done` → **消息静默丢失**
      → 强制 `affectedRows === 1`，否则抛错**回滚整个事务**；
      并给事件认领加 `AND status = 'pending'` 守卫（防并发重复投递）
- [x] **#97** 缺 `notificationId` 的事件被 `continue` 跳过
      → 永远卡在 `pending`，被 dispatcher 每 2 秒重复扫描
      → 显式标记 `failed`，让它可见、可查、可人工处理
- [x] **#98** 流程缺口：Worker 投递链路没有任何自动检查
      → 新增**回归链第 17 步**「Worker 投递链路自检」
      （容器内 · 测试库 · 测试 Redis db=1 · 独立队列名），**25 项断言**，
      并内含**反向验证**：复刻修复前的实现跑同一场景，
      断言「旧实现确实会静默失败、新实现确实会拦住」
- [x] 顺带收紧：回退只处理 `status = 'pending'` 的行
      （终态事件不得被改回 `pending`，否则已送达的通知会被重复投递）；
      超过 `MAX_DELIVERY_ATTEMPTS = 10` 标记 `failed`，不再无限重试

**配套**

## Phase 42 — 幂等键的作用域：路由模板会让「一把钥匙开两个资源」互相串扰

**起因**：Phase 41 修完 #139（`notification.push()` 静默丢弃参数）之后，
沿「**参数/键被静默丢弃**」这条家族继续查 —— 下一个命中的是**幂等键本身**。

- [x] **#140** 幂等 scope 用的是**路由模板** → 同一把钥匙开两个不同资源会互相串扰
      → scope = `METHOD:${request.route.path}:u{userId}`，而 `route.path` 是模板
        （`/connections/:id/contact-grant`），不是实际路径
      → 后果：第二个请求被判成**回放**、返回**第一个**资源的响应，
        而第二个资源**根本没被写入** → 客户端收到 200（**静默的数据丢失**）
      → 实测：`PUT /connections/58|59/contact-grant` 用同一把钥匙 →
        第二个响应 `data.id` 是 **58**，库里只有 **1 条**授权记录
      → 处置：scope 改用**实际路径**（`request.originalUrl` 去查询串）；
        请求指纹扩到「方法 + 实际路径（含查询串）+ body」→
        同一路径不同查询串/请求体仍返回 409 `IDEMPOTENCY_CONFLICT`
      → 配套迁移 `1730000004000-WidenIdempotencyScope`：
        `scope` 由 VARCHAR(64) 放宽到 VARCHAR(255)
        （实际路径更长，长路由 + BIGINT id **会超过 64 字符** → 不放宽就 500）
      → 配套 `idempotency-scope.e2e-spec.ts`（3 例：1 条 #140 + 2 条对照）
      → 反向验证：未修代码上真红（`data.id` 58 ≠ 59），修复后幂等相关 13/13 全绿
      → 契约同步：API-SPEC 与 CONCURRENCY-DESIGN 明确「路径取**实际路径**（含资源 id）」
- [x] **#141** 客户端**每次请求都换一把新的幂等键** → 幂等能力在真实链路上形同虚设
      → 管理后台的 axios 请求拦截器每次都 `randomId()`（401 重试也换新的）；
        小程序每次 `generateId()`
      → 后果：「首次其实写成功了、只是响应丢了」的重试被当成**新请求** → **重复创建**
      → 已做：管理后台「已经有钥匙就不再覆盖」；小程序钥匙生成上移到 `request()` 一层
        （401 重试走 `{ ...opts }` → 天然沿用），并支持显式传 `idempotencyKey`
      → **仍存在的缺口（如实记录）**：用户**手动重试**是两次独立动作，
        要去重得由 UI 层「一个动作一把钥匙」，目前各页面**没有**持有这个键；
        两端也都没有测试运行器，本轮**没有**为该行为写自动化测试
- [x] **顺带**：撤销 `PROCESS` 权限后夹具诊断必然失败 → 控制台噪声被误读成测试失败
      → 处置：先用 `information_schema.user_privileges` 探针有没有 `PROCESS`，
        没有就**根本不查** `innodb_trx`；探针与诊断期间把 logger 临时换成静默版
      → 实测：chain53 每轮 4 条 Access denied 噪声 → chain55 起 **0 条**

**配套**
- [x] 新增 `idempotency-scope.e2e-spec.ts`（3 例）
- [x] 新增迁移 `1730000004000-WidenIdempotencyScope`（幂等：先查列类型再 ALTER）
      并已应用到**业务库**（改动前先做了备份 `20261117-010714`）与测试库
- [x] 改 `idempotency.interceptor.ts`（scope 与请求指纹）、`helpers.ts`（探针 + 静默 logger）
- [x] 改前端：`apps/admin-web/src/api/http.ts`、`apps/miniprogram/src/services/request.ts`
- [x] 契约同步：`docs/API-SPEC.md`、`docs/CONCURRENCY-DESIGN.md` 的幂等条目

测试库残留事务 **0**、业务库 `users` = **1202**（未污染）。

## Phase 43 — 迁移一致性：部署不跑迁移、迁移清单有两份（新增第 14 层校验）

必须**手工**到服务器上补跑 —— 那一刻才意识到：
**部署流程里根本没有「跑迁移」这一步**。这类漂移**天然只在业务库暴露**
（测试库每次重建并跑迁移），于是补一层**对账**把它变成可自动发现的问题。

- [x] **#142** 部署流程**不执行迁移** → 代码与业务库表结构悄悄漂移
      → deploy 原流程：同步 → 构建 → `up -d` → 健康检查（**中间没有迁移**）
      → 后果：代码已按新结构工作、库里还是旧结构 → **运行时才报错**
        （#140 的 `scope` 若没补迁移 → `Data too long` → 500）
      → 处置：`deploy.sh` 在 **`up -d` 之前**用新镜像跑一次迁移

        - 切流量**之前**：旧容器仍在服务旧代码，迁移是**加法式**的 → 旧代码完全兼容
        - 迁移失败 → **中止部署**；`--build-only` → **不动库**

      → `migrations/index.ts`（应用用）与 `data-source.ts` 的数组（**CLI 用这份**）各抄一份
      → 漏加的后果：那条迁移**永远不会被应用**，且**没有任何报错**
      → 处置：`data-source.ts` 改为 `import { migrations } from './migrations'` → 单一事实来源
- [x] **#144 流程缺口** → 新增**第 14 层校验** `check-pending-migrations.sh`
      → R1 清单 ↔ 文件一致（失败）/ R2 业务库无未应用迁移（失败）/

## Phase 44 — 临时预览版：公网接入层、离线兜底，以及一个「必崩包」缺陷

**起因**：用户要求「先把临时预览版发布出来，让客户初步体验」。
但两件事卡着：① 小程序资质还没注册（拿不到 AppID 与上传密钥）；
② 后端在 NAT 后、无公网 IP，校园网屏蔽了 81% 的免费内网穿透。

**做法**：把「等凭据」和「等网络」这两件事**都从关键路径上移走**——
工程侧全部备好，凭据一到就是一条命令；同时做公网接入层与离线兜底。

- [x] **公网接入层**：临时公网服务器 + SSH 反向隧道
      → 边缘 nginx（`deploy-public-edge.sh`）+ 校园机隧道（`tunnel-public-edge.sh`）
      → 拓扑：边缘 nginx → 隧道 → 校园机 compose nginx（`/` 管理后台、`/api/` API）
      → 选「校园机主动出站」是因为校园 NAT 只放行 SSH 转发端口，
        而校园机**出站**是通的
      → 端到端自测 `check-public-edge-e2e.sh`：真跑一遍整条链，
        并反向验证「端口被占用时必须报错、不得静默打错服务」
      → 隧道守护的三个真缺陷（都当场修掉）：
        ① HTTPS 分支两个 server 块都监听 443 → `nginx -t` 直接报错；
        ② 收到 TERM 只杀 ssh 子进程 → `while true` 又拉起来 → 端口一直被占；
